같은 서버·별도 서버·VM 후보, 기존 업무 피크, 추가 자원과 관리 담당을 확인합니다.

03.2

백업 보관 기간·서버 외부 보관 여부·복원 시험 기록·허용 중단시간과 데이터 손실 범위를 확인합니다.

03.3

연결과 문자 저장을 검증할 시험 환경이 있나요?

DB 상세 버전, 드라이버·클라이언트 구성, 한글·특수문자 사례, 시험 데이터 확보 방법을 기록합니다.

제공 정보와 현장 확인은 구분합니다. 자원 배치나 드라이버 버전은 총 RAM·디스크 여유만으로 확정하지 않습니다.

04.1

1차 발주를 저장하면 어떤 데이터가 함께 바뀌나요?

번호 생성, 필수 상태값, 트리거, 수량 갱신, 저장과 공급처 전송의 경계를 설명받습니다.

04.2

화면에서 보이는 잔량과 DB 값이 다른 경우가 있나요?

계산 열·집계 기준·미송 종료·입고 반영 지연·클라이언트 검증을 실제 완료 건으로 대조합니다.

여기 적는 객체명은 현장에서 확인한 값입니다. 기존 코드나 업무 프로시저의 재사용을 전제로 하지 않고, 자체 구현이 맞춰야 할 데이터 규칙을 조사합니다.

주문과 취소 수집 인터뷰

실제 사용하는 판매처와 처리 순서를 확인합니다. 화면의 버튼 이름만으로 수집 방식이나 외부 상태 변경 여부를 단정하지 않습니다.

화면에 10개 그룹·27개 계정이 표시됩니다. 실제 사용 여부·거래법인·주문/취소 권한을 확인하고 대표 계정을 아래에 기록합니다.

05.1

어떤 주문과 취소가 아침 수집 대상인가요?

기준시각·상태·판매 계정, 누락 여부를 확인하는 화면이나 건수를 기록합니다.

05.2

취소 수집과 실제 취소 처리는 어떻게 구분하나요?

취소수집·취소처리(F7)·출고중→미출고가 별도입니다. 수신과 수요 반영 시점, 충돌 처리의 실제 사례를 연결합니다.

05.3

같은 주문이 다시 들어오거나 취소가 먼저 오면 어떻게 되나요?

주문상품 식별자, 수량이 누적인지 증분인지, 상태 시각과 중복 기준을 기록합니다.

05.4

한 판매처가 실패하면 어디까지 진행하나요?

재수집 범위, 기존 성공 건 유지, 발주 대상 보류·진행 기준, 확인 담당을 기록합니다.

복합 조건 사례 확인표

설명만으로 정책을 확정하지 않습니다. 각 조합을 대표하는 완료 건을 찾아 남은 수량과 실제 처리 결과를 연결합니다.

아래 여섯 줄은 실제 사례를 찾기 위한 조합입니다. 택배와 익일 입고는 겹칠 수 있으며, 여섯 가지로 모든 경우를 고정하지 않습니다.

조건 조합확인할 판단실제 거래처 / 사례 / 근거
당일 + 자동 후송첫 입고 후 남은 물량의 도착일과 대기 기준
당일 + 재발주 필요납품 종료 확인 후 현재 필요한 수량 재계산
익일 + 자동 후송익일 첫 납품과 이후 미송의 도착일을 구분
익일 + 재발주 필요발주 당일 미입고를 재발주 사유로 삼는지 확인
택배 + 자동 후송배송 중 수량과 아직 보내지 않은 수량 분리
택배 + 재발주 필요배송 중 물량을 제외하고 납품 종료 잔량 확인

기존 미송을 유지한 채 새 발주를 내는 조건, 취소·재배정 확인과 결정 담당을 기록합니다.

11.1

발주 당시 재고·주문·미송 상태를 복원할 수 있나요?

스냅샷·수불·변경 이력의 보존 기간, 기록 시각, 당시 값과 현재 값의 구분을 확인합니다.

11.2

최초 1차 발주와 이후 수정·보충 발주를 어떻게 구분하나요?

발주 타임 숫자만으로 판단하지 않고 최초 저장·전송·수정 이력을 연결합니다.

11.3

자동 계산이 맞았는지 어떤 기준으로 판단하나요?

거래처 일치, 수량 차이, 과다·과소 발주, 필요일 미충족, 예외 검토시간을 함께 봅니다.

발주 이력은 판단의 결과입니다. 정책·당시 상태·예외 사유가 없으면 규칙 후보로 남기고 확인 수준을 표시합니다.
