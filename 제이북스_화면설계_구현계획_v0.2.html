이번 단계는 PRD를 화면·상태·개발 작업으로 연결하는 설계다. 함께 제공하는 화면은 가상 상품·계정·견적·주문으로 동작하는 오프라인 시제품이다. 실제 수집·Oracle 저장·예약 실행을 구현하거나 연결한 결과가 아니다. 화면에서 바꾼 예시는 새로고침하면 초기화된다.

01. 먼저 검토할 화면 흐름

  1. 오전 현황: 수집이 완전한지, 저장 가능한 상품과 확인할 상품이 각각 몇 개인지 본다.
  2. 수집센터: 예약 설정 또는 지금 수집을 선택한다. 수집만과 1차 발주까지를 구분한다.
  3. 발주 검토: 상품별 부족분·적정재고·유효 공급·거래처 비교 근거를 본다.
  4. 미송관리: 원발주의 잔량 유지·종료·입고일을 확인하고 발주 후보를 다시 계산한다.
  5. 실행 이력: 수집, 보류, 수정, 저장 결과를 대조한다.

화면의 기본 완료 경계는 제이북스에 거래처·부수를 1차 발주 상태로 저장하고 대조하는 것이다. 실제 공급처 주문·결제는 화면 흐름에 포함하지 않는다.

UI-02. 예약과 수동 수집

예약 설정에는 시간대, 실행 요일·시각 또는 반복 간격, 대상 계정, 활성/중지, 후속 처리 범위를 둔다. 수동 실행에는 전체/선택 계정, 증분/기간 재수집, 수집만/1차 발주까지를 둔다. 예약 일시중지는 수동 실행을 막지 않는다.

공통 실행 대기열이 같은 계정의 중복 반영을 막는다. 같은 범위의 요청은 기존 실행에 연결하고 더 늦은 종료시각·다른 범위는 후속 작업으로 남긴다. 운영 구현에서는 서로 다른 계정을 판매처 호출 제한 안에서 처리한다. 시제품은 흐름을 검토하기 위해 한 번에 한 작업을 처리한다.

검토용 예약 실행 버튼은 설정을 읽어 예시 작업 1건을 발생시킨다. PC가 꺼진 동안 동작하는 실제 스케줄러, 주기 실행, 외부 판매처 조회는 없다. 실제 개발에서는 서버 측 예약 실행과 누락 예약의 통합 보충 수집을 구현한다.

실프로그램 반영: 계정 표는 주문 수신·취소 수신·내부 반영·대조 상태를 구분한다. 운영 계정 원장은 10개 그룹·27개 표시를 출발점으로 활성/법인/권한을 검증한다. 시제품 조작 대상은 3개 가상 계정이며, 실제 화면 목록은 읽기 전용 참고표다. 취소 반영 대기 예시를 켜면 수집 성공 후에도 모의 저장은 막히고 별도 반영 확인 후 풀린다.

운영의 장애주문은 원천과 보정 전후를 보존하고 재처리한다. 출고 충돌은 정상 반영 대기와 별도이며 ‘출고중 → 미출고’를 자동으로 누르거나 운영 검토를 가상의 반영 확인 버튼으로 대체하지 않는다. 장애주문 보정·출고 충돌의 실제 화면 연결은 후속 구현이다.

UI-03. 상품별 판단과 적정재고

상품 상세는 다음 순서로 읽는다.

  1. 현재 확정 수요와 세트 구성품 수요.
  2. 최근 3주 W1/W2/W3와 이전 일평균 수요, 적용 가중치.
  3. 선택 거래처의 보충기간 H와 안전재고 SS, 목표재고 S.
  4. 물리 재고 I·유효 입고예정량 P와 최종 후보 Q.
  5. 크롤링 선정·제외 이유와 공급처별 선택·탈락 근거.

시제품의 대표 상품은 PRD 예시를 사용한다. W1/W2/W3=14/7/7, 이전 일평균=1, λ=.7, H=3, SS=2이면 S=7이다. 미출고 4, 물리 재고 3, 유효 공급 2이면 Q=6이다. 가중치·공급기간·안전재고와 거래처 조건은 고객에게서 추정한 실제 값이 아니다.

조회 결과가 누락된 공급처는 품절로 바꾸지 않는다. 시제품의 ‘예시 조회 완료’는 검토 시나리오를 다음 상태로 이동시키는 기능이며 실제 견적을 가져오지 않는다. 대표 상품의 거래처를 바꾸면 해당 예시 조건의 H·SS·S·Q를 다시 계산한다. 다른 상품의 목표재고는 단순화한 고정 예시이며 전체 상품의 예측 엔진이 아니다. 네 공급처의 후보 수량을 각각 저장하지 않는다.

집계·필터: W1/W2/W3는 겹치지 않는 주간 순수요다. C7/C14/C21이 같은 시점 누적임이 확인된 경우만 차분 변환한다. 화면에 온라인/오프라인 범위·취소 처리 기준·집계시각을 제시하고, 세트 3달 수주와 21일 학습 범위를 구분한다. 이 의미 검증을 시제품 예시 값으로 대신하지 않는다.

회차: 시제품은 10·11·16·18 등의 임의 가상 회차를 선택해 저장 이력에 남긴다. 실제 운영 코드는 DB 확인 후 구성하며 시각으로 해석하지 않는다. 기존 UI의 저장/F7·상세 일괄 수정·복사 경로와 충돌하는 변경은 재조회로 확인한다.

UI-04. 미송 확인과 재계산

검토 예시는 발주 10부, 입고 6부, 미확인 잔량 4부다. 필요한 날짜 안의 잔량 유지·입고가 확인되면 4부를 유효 공급으로 배분한다. 잔량 종료가 확인되면 최신 수요로 필요량을 재계산한다. 입고일이 필요일보다 늦거나 여전히 불명이면 자동 저장 보류를 유지한다.

입고 예정 확인은 실물 입고가 아니다. 잔량 확인을 했다는 이유로 창고 재고를 올리지 않는다. 사실 입력에는 확인 방식·시각·근거가 필요하며 운영 구현에서는 원발주별 수불과 업체 답변을 연결한다.

정책 기본값: 거래처의 주문유효기간·입고 시일·마감시간·발주방식·법인 값을 먼저 매핑한다. 유효기간 만료와 미송 소멸, 전송 방식과 택배 여부를 분리한다. 원발주 연결과 근거가 없으면 자동 종료·재발주를 보류한다. 시제품은 이 원칙을 안내하며 마스터 동기화 자체는 구현하지 않는다.

04. 자체 구현 모듈과 데이터 경계

초기 구현은 기능별 모듈을 가진 하나의 애플리케이션과 작업 워커 구조를 우선 검토한다. 필요성이 확인되기 전에 여러 서버로 분리하지 않는다. 런타임과 DB 드라이버는 정확한 Oracle 버전·수집 방식·운영 환경 확인 후 확정한다.

기존 프로그램의 코드·스크립트·업무 함수를 재사용하지 않는다. 기존 DB의 무결성 조건과 트리거는 분석해야 하며 자체 코드에서 이를 위반하지 않아야 한다. 이 문서의 논리 명칭은 실제 테이블명·컬럼명·API 주소를 뜻하지 않는다.

05. 고객사 내부에서 진행할 DB 조사 순서

접근은 고객사가 정한 절차에 따라 수행하며, 최초 조사는 읽기 전용 권한·제한 표본으로 진행한다. 운영 변경 없이 결과를 대조할 수 있는 시험 환경과 복구 절차부터 확인한다. 실제 접속정보를 이 문서에 기록하지 않는다.

순서 조사 대상 확보할 산출물 통과 기준
DB-01 버전·문자셋·권한·접속 조건·시험 DB·백업/복구 접속/조회 범위와 시험 계획 정확한 버전과 고객 측 접근 절차 확인
DB-02 테이블·뷰·키·제약·트리거·채번·후속 전송 실제 객체 관계도·저장 의존성 목록 1차 저장과 공급처 전송 경계 설명 가능
DB-03 주문·취소·계정·수집 이력 원천↔수주 키, 상태 전이·완전성 계약 27개 표시의 활성·법인 대조, 생성·부분/늦은 취소·장애주문 추적
DB-04 상품·판본·세트 구성·수불 구성표와 배분/조립 단위 겹치는 세트 2개와 실물 조정 전후 일치
DB-05 현재고·예약·적정재고·변경 이력 총량/예약 차감 정의·과거 시점 복원 범위 같은 수요·재고 이중 가감 없음
DB-06 원발주·입고·배송·취소·잔량 종료 원발주-부분입고 매칭, 미송 유효성 10부/6부 사례와 연속 발주 사례 설명
DB-07 거래처·출판사·공급률·조건·발주 회차 직거래/도매·크롤링 예외·달력·마감 정책 유효기간/입고 시일/마감/법인·65 단위·복수 회차를 실제 이력에 연결
DB-08 3주 및 이전 주문·취소·입고 이력 비식별 계산 표본·당시 상태·누락표 C7/14/21와 원천 주간 수요 대조, 온라인·오프라인/세트 범위 확정
DB-09 최종 저장·동시 수정·화면 반영 시험 저장 계약·대조 쿼리·복구 절차 F7·상세 수정 경로와 충돌 검증; 외부 전송 없이 거래처/부수 일치

DB에서 확인할 수 없는 당일 견적·계약 변경·전화 확인은 해당 표본에만 보완한다. 테이블명이나 이벤트 의미가 밝혀지기 전에 대량 조회 SQL 또는 운영 쓰기 SQL을 확정하지 않는다.

W02의 작업 발생기는 운영 예약과 연결하기 전 가상 시계로 검증한다. W03~07은 가능한 범위에서 계산 전용으로 진행하고 W09 시험을 통과하기 전 운영 저장을 개방하지 않는다. 위 목록은 작업 범위이며 일정·비용 확정표가 아니다. 데이터 접근·수집 경로를 확인한 뒤 각 작업을 구현·시험 단위로 나누어 산정한다.

07. 시제품 검토 시나리오와 한계

순서 검토 행동 기대 결과
1 초기 오전 현황 열기 실패 계정과 확인 필요 상품 표시; 저장은 수집 완전성 때문에 보류
2 수집센터에서 실패 계정 재수집 예시 수집 완료, 발주 저장 건수는 그대로
3 같은 범위로 수집을 연속 요청 진행 중인 예시 작업으로 연결; 중복 반영 없음
4 대표 상품의 최근 주문 또는 거래처 변경 목표재고와 후보 부수가 연결되어 변경
5 미송 잔량 4부를 필요일 안의 입고로 확인 실물 재고는 그대로, 유효 공급에만 반영; 해당 발주 필요량 재계산
6 견적 누락 상품의 예시 조회 완료 누락 상태가 해소되어 네 공급처 비교 가능
7 저장 가능한 후보의 모의 저장을 두 번 실행 첫 실행의 후보만 완료, 같은 예시 발주 중복 없음
8 검색 결과 없음·수집 실패·빈 계정 입력 보기 빈 목록·오류·입력 검증 상태가 명확히 표시

시제품은 화면 흐름과 대표 계산의 검토 범위다. 실제 스케줄러, 판매처 인증·API/파일 수집, Oracle 트랜잭션·수불·전송 경계, 분산 실행권, 실제 금액 비교, 운영 데이터 복구를 구현하거나 검증하지 않았다. 세트의 복잡한 조립·부분입고 매칭·여러 납기의 시간별 배분은 설계 및 수용 테스트에 남아 있다. 예시 입력을 실제 저장 계수나 실제 공급처 조건으로 사용하지 않는다.

v0.2 시제품 보강: 취소 수신/내부 반영 표시, 반영 대기 시 모의 저장 보류, 별도 예시 반영 확인, 여러 회차 선택과 모의 저장 이력, 실제 화면 27개 계정의 비활성 참고표, 산식·세트 필터·마스터 의미 안내를 추가했다. 원발주 DB 매칭, 장애주문 편집·재처리, 모든 동시 수정·초안 개정 계약은 운영 구현 전 검증 항목으로 남는다.

다음 구현의 첫 착수점: 고객사에서 DB-01~03의 읽기 범위와 주문·취소 표본을 확보하여, 실제 테이블·이벤트를 정규화 계약에 연결한다. 화면 검토와 데이터 조사는 병행할 수 있다.
